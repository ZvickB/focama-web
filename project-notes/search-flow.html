Current Implemented Flow

Focamai Search Flow

This is the live guided flow as wired today in the homepage and Render backend. It documents current behavior only: discovery, refinement, shortlist lock, async enrichment, preview mode, and retry advice.

Provider reality: the main homepage route is still /api/search/rainforest-discover, but the route currently uses the Oxylabs-backed Amazon path under that Rainforest-named surface. The current UX may name Amazon when Amazon is the active source, while backend/provider logic stays flexible. SerpApi is not part of the active homepage flow.

Parallel

Starts at the same time as another request and does not wait for it.

Blocking

User waits for this response before the next product state can appear.

Async

Runs after finalize returns. The UI merges this work in later.

Two Requests Fire On Submit

Starting a search launches discovery and the follow-up question in parallel. The old third “framing fields” lane is not part of the current implementation anymore.

Parallel lane A

Discovery

GET /api/search/rainforest-discover validates the query, resolves the Amazon domain, checks discovery cache, fetches product artifacts when needed, stores a discoveryToken, and returns a preview set plus a server-owned candidate pool.

Returns preview data + token
Parallel lane B

Refine

GET /api/search/refine generates one short follow-up question plus helper copy. If it fails, the frontend falls back to a local generic prompt so the flow keeps moving.

Question-first experience
1

User Starts With Just The Product

Homepage

The homepage asks only for the product topic first. Helper copy explicitly says budget, size, and other details come next, so the initial query stays lightweight.

Primary CTA

Start search

Examples shown

Travel stroller for airplane, ergonomic office chair, lego botanical set.

2

Discovery And The Follow-Up Prompt Race In Parallel

GET /api/search/rainforest-discover GET /api/search/refine Question visible before finalize

The user sees the refinement area as soon as the follow-up prompt is ready. Discovery can still be loading underneath. The primary button stays disabled until discovery has returned a valid discoveryToken and preview set.

Refine copy

The more you share, the better the picks. The user can type while the suggested prompt is still being generated.

Discovery output

candidatePool, previewResults, resolved amazonDomain, and a trusted discoveryToken.

3

Preview Mode Is Available Before Finalize

Just show me results No AI shortlist yet

Once discovery is ready, the user can click Just show me results. That reveals the preview grid immediately and tracks a preview impression set, but it does not run finalize and it does not claim those cards are the focused picks.

User-facing note

No AI refinement — results based on your search only.

Important distinction

Preview results are real product cards, but not the locked 6-pick shortlist.

4

User Adds Context And Clicks “Show Focused Picks”

Refine step

The user can write natural-language notes about price, style, fit, use case, or what to avoid. The frontend sends the query, resolved Amazon domain, discovery token, follow-up notes, retry metadata, and request mode. It does not send the candidate pool itself.

Request modes in use

guided_refined when notes are present, guided_empty_notes when the user skips details.

Server trust boundary

Finalize rebuilds the pool from guided cache using discoveryToken. Browser-posted candidate data is not part of the trusted path.

5

Finalize Locks The 6 Winners

POST /api/search/finalize Shortlist response

Finalize validates the body, rate limits by IP, resolves the discovery snapshot, trims notes, then asks Haiku to lock the shortlist. The fallback path is deterministic, and partial valid Haiku output is topped up rather than discarded.

Happy path

selection.strategy: 'haiku_lock'

Recoverable partial path

selection.strategy: 'haiku_lock_topped_up'

Fallback path

selection.mode: 'rules_fallback' when Haiku yields nothing usable.

6

Cards Render Immediately After The Lock

Final results grid Get 6 picks

The blocking finalize response returns the shortlisted cards right away. The frontend treats the grid as metadata-first: image, title, price, source, rating, review count, and badge labels. It does not wait for product-detail enrichment before showing the six results.

What arrives immediately

Shortlist cards, selection/debug metadata, analytics events, and badge reveal timing.

What may still be missing

feature_bullets, fit_reason, and caveat are usually still on the async path.

7

Product Details And Mini Enrichment Run Fully Async

Background work

After the finalize response has already been sent, the backend fetches product details for the selected IDs, merges those details into the shortlisted candidate pool, runs mini enrichment, writes enrichment back into the discovery snapshot, and emits an enrichment-ready event keyed by the discovery token.

Stored enrichment fields

feature_bullets, fit_reason, caveat, model, generated timestamp, and preserved order.

Important rule

Async enrichment explains the locked shortlist. It does not change the winners.

8

SSE Is First, Polling Is Fallback

GET /api/search/enrichment-stream GET /api/search/enrichment Best effort

The frontend opens EventSource against /api/search/enrichment-stream first. If SSE is unavailable or errors, it silently falls back to polling /api/search/enrichment every 1.5 seconds for up to 30 seconds.

SSE response shape

{ ready: true, entries, model } or { ready: false }

Poll response shape

Same contract, but fetched repeatedly until enrichment is ready or timing settles.

9

The Modal Starts Useful, Then Gets Smarter

Product modal

Opening a card shows the main product facts immediately. If async enrichment has not landed yet, the modal shows an ambient “Analyzing your pick…” state. When enrichment arrives, the modal fills in the “Why we picked it” explanation and the honest caveat.

Before enrichment

Title, image, price, rating, source-specific CTA, and either feature bullets or the base description when bullets are not available yet.

After enrichment

fit_reason and caveat appear, plus feature_bullets when the async detail fetch found them.

10

Retry Is Suggestion-Led

Retry panel POST /api/search/retry-advice

After final results, the active UI asks what felt off and requests a better next search. The returned suggestion is editable, and using it resets the page into a fresh search flow.

Live button copy

Get a suggestion followed by Use this search

Archived — same-pool retry

The same-pool retry path (excluded IDs, retryCount > 0, retry_exhausted) exists only in code archives. The frontend always sends retryCount: 0 — those server branches are unreachable from the active flow.

Timing And Observability Reality

Exact numbers vary by cache hit, provider latency, and model speed. What matters now is which stages block and which stages are deferred.

Discovery
Cache-first
Returns cached preview results immediately when available. Misses call the Oxylabs-backed Amazon path behind the Rainforest route name.
Refine
Independent lane
Does not wait for discovery. The frontend has a local fallback prompt if the API call fails.
Finalize
Shortlist lock only
Server-Timing currently measures body read, cache lookup, Haiku, and total. Product detail latency is no longer in the blocking response.
Enrichment
SSE-first async
Product details plus mini enrichment run after finalize responds. Polling exists only as a fallback.

Current Guardrails

Rule 1

The candidate pool is server-owned

The browser sends a token, not the authoritative pool. Finalize reconstructs from the discovery snapshot.

Rule 2

Shortlist stays at 6

Preview can show a broader discovery set, but the guided product output is still the final six picks.

Rule 3

Finalize is thin on purpose

Haiku locks the shortlist in the blocking path. Product-detail fetches and mini enrichment stay off that critical path.

Rule 4

Preview is not the same as focused picks

Just show me results is a discovery preview, not the guided shortlist.

Rule 5

Enrichment explains, not reranks

Async detail work can add bullets, fit reasons, and caveats, but it cannot replace the locked winners.

Rule 6

Amazon-first UX, flexible internals

The current UI may name Amazon when Amazon is the active source. Backend/provider logic and normalized product data should stay flexible, without making today's Amazon-first UX vague.
