Current Implemented Flow

Focamai Search Flow

How the app works now — from the user's first query through discovery, refinement, shortlist selection, and async enrichment. This reflects wired production behavior, not planned future architecture.

Provider note: The production plan is to use Rainforest API as the primary product data source for both discovery and post-finalize product detail enrichment. During development, Oxylabs is substituted to conserve Rainforest credits. SerpAPI is preserved as a secondary fallback for discovery.

Parallel

Fires at the same time as other requests; does not block the flow.

Blocking

User waits for this before the next state becomes visible.

Async / Polled

Fires after a blocking response returns; UI polls and merges results when ready.

Three Requests Fire Together On Submit

All three start the moment the user submits their query.

Blocking — Lane A

Discover

Validates the query, fetches products via Rainforest (primary) or SerpAPI (fallback), cleans the pool to 20 candidates, writes to guided cache, and returns a preview set plus a discoveryToken.

~6.5s cold / ~150ms cached
Blocking — Lane B

Refine (question_fast)

Uses a lightweight model to write one short follow-up question. Returns as soon as the question is ready; does not wait for discovery to finish.

~1.7s
Background — Lane C

Framing Fields

Runs background query framing in a separate lane. Result is held client-side for the timing panel only — not stored server-side, not consumed by finalize.

~4.4s (doesn't block)
1

User Enters A Product Query

Homepage

The user types a product search — e.g. wireless headphones — into the central search input and submits. The three parallel requests launch immediately. The step indicator advances to Search.

Helper copy shown

"Just the product for now — budget, size, and other details come next."

Input sent

The raw query string. Nothing else at this stage.

2

Refinement Question Appears

POST /api/search/refine Blocking for question

The refine response (~1.7s) arrives first. The homepage expands to show the AI-written follow-up question, a textarea labelled Your answer, and the two action buttons. Discovery is usually still running at this point.

Eyebrow shown

"The more you share, the better the picks"

Buttons shown

"Just show me results" (skip, no AI) and "Show focused picks" (primary). Skip is active immediately; primary is gated on discovery finishing.

3

Discovery Finishes — Preview Set Available

POST /api/search/discover Blocking for token

When discovery returns, the frontend holds the discoveryToken and the preview candidate set. The Show focused picks button becomes active. The user can optionally reveal the raw preview set by clicking Just show me results.

Cache hit

On a cache hit the token is available within ~150ms — the primary button becomes active almost immediately.

Preview results

Clicking "Just show me results" shows the unfiltered preview set and skips finalize entirely.

4

User Answers The Follow-Up And Clicks "Show Focused Picks"

Refinement step

The user types their context — budget, use case, priorities, what to avoid — and submits. The step indicator advances to Refine. Result skeletons appear below while finalize runs.

What is sent to finalize

Query, discoveryToken, follow-up notes (truncated to 500 chars server-side), retry count, and excluded candidate IDs on retry passes.

What is not trusted

The browser never posts the candidate pool. Finalize reconstructs it server-side from the discovery cache using the token.

5

Finalize Locks The Shortlist And Fetches Product Details

POST /api/search/finalize Blocking Fires mini enrichment async

The server reconstructs the full candidate pool from guided discovery cache, uses nano to lock the 6 winners (~2s AI call), then fetches Rainforest product detail for each of the 6 locked ASINs in parallel. The blocking response includes cards with feature_bullets when detail calls succeed. After the response is sent, mini enrichment fires async to write fit_reason and caveat per pick into the discovery cache.

Response shape

flowPath: 'nano_lock', 6 shortlist cards with image, title, price, merchant, ratings, badge hint, and feature_bullets.

Fallback

If a Rainforest product detail call fails, that card returns feature_bullets: []. The shortlist is never blocked by a failed detail call.

Nano model

Only viable fast model for locking. Mini was rejected — 8s+ lock time makes it unsuitable for the blocking path.

Async enrichment

Mini fires after the response returns. Writes fit_reason + caveat to selection.enrichment in the discovery cache.

6

Cards Appear — Metadata Only

Results grid Step indicator: Get 6 picks

The 6 result cards reveal with entrance animations. Cards show image, title, merchant/source, price, ratings, and a deterministic badge label assigned by frontend heuristics. No AI copy on the card surface. feature_bullets are immediately available in the modal for cards where detail calls succeeded.

Badge labels

Frontend-owned. Deterministic heuristics assign scan-friendly labels (e.g. Best Value, Top Rated) after the shortlist arrives, with a slight staggered reveal.

Modal on open

Immediately shows product facts and feature_bullets. AI copy sections (Why this pick / Possible drawbacks) show a shimmer skeleton until enrichment arrives.

7

Frontend Polls For Enrichment

GET /api/search/enrichment Async polling

The frontend polls every 1.5 seconds (30-second timeout) with ?token=&query=. The endpoint returns { ready: false } until mini has finished writing, then { ready: true, entries: [...] } where each entry contains candidateId, fitReason, caveat, and feature_bullets.

On ready

Frontend merges enrichment into results by candidateId. Modal AI copy sections fill in. enrichmentReady = Boolean(item?.fit_reason).

Enrichment guardrail

Enrichment can only explain the shortlist — it cannot re-rank or replace winners chosen by nano.

8

Modal Shows Full Explanation

Product detail modal

Once enrichment arrives, the modal for any open card shows "Why this pick stands out" (fit_reason) and "Possible drawbacks" (caveat), written by mini to read like a trusted assistant — specific to the user's stated context, with an honest caveat, no superlatives.

Always visible

Title, price, merchant, ratings, feature_bullets (manufacturer copy). These do not wait for enrichment.

Copy tone rule

AI copy must include at least one honest drawback or caveat. The office chair example in CLAUDE.md is the reference.

9

Optional: User Gives Feedback And Retries

Retry loop Re-runs finalize

After results appear, the user can say "Didn't find anything you like? Tell us why." Retry requires written feedback, excludes the rejected shortlist IDs from candidate selection, reuses the same guided discovery context, and is capped at 2 passes. Previous picks collapse into a "Previous picks" section.

What changes

Excluded IDs are passed to finalize. The candidate pool is the same 20 from discovery cache — not re-fetched.

Guardrail

Hard exclusion of rejected IDs. If the pool is small this can be strict — broadening discovery rather than reusing rejects is the preferred path if it becomes a problem.

Key Rules

Rule 1

Candidate pool is server-owned

Finalize always reconstructs from the guided discovery cache. The browser never posts candidate data. The discoveryToken is the only trusted reference.

Rule 2

User context is the dominant signal

Follow-up notes carry more weight than query framing or prior rankings. The shortlist should reflect what the user actually said, not the backend's early assumptions.

Rule 3

Cards reveal only after the shortlist is settled

No recommendation-like cards show before finalize returns. Preview results from "Just show me results" are clearly unfiltered — not AI picks.

Rule 4

Enrichment explains, never re-ranks

Mini's job is to write honest fit reasons and caveats for the 6 nano picked. It cannot change who won.

Rule 5

Shortlist stays at 6

6 results end to end. Not a marketplace wall. Don't add more without an explicit product decision.

Rule 6

Stay vendor-agnostic in product shape

Rainforest is the integration layer, not the product identity. The frontend should not be redesigned around any specific data provider.
