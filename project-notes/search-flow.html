4. Finalize — Shortlist Lock
POST /api/search/finalize
Locks the 6-pick shortlist
▼

Input Validation

  • 32 KB body limit
  • Candidate pool cap: 30
  • Follow-up notes truncated to 500 chars
  • Rate limited (same 15/10s window)

Pool Reconstruction

  • Reads token-scoped session snapshot from cache
  • Never trusts browser-posted candidate data
  • Sanitizes: removes zero-price items, retags Amazon links
  • If Prime explicitly requested → narrows to Prime-eligible candidates

Key Files

  • backend/lib/handlers/finalize-handler.js
  • backend/lib/ai-selector.js
Haiku Shortlist Lock

▼

Ranking Criteria (in order)

  1. Inferred product fit to user's stated needs
  2. Quality confidence (rating, review count, trustScore, recognized brand)
  3. Price/value alignment
  4. Shortlist variety
  5. Raw Amazon search position (final tiebreaker)

Fallback Strategy

  • Full valid response → haiku_lock
  • Partial valid subset → tops up from deterministic fallback → haiku_lock_topped_up
  • Zero valid picks → full deterministic rules fallback → rules_fallback

Model

  • Default: claude-haiku-4-5-20251001
  • Override: OPENAI_FINALIZE_MODEL env var

5. Async Enrichment (after finalize responds)
Background Enrichment Starts
Product detail fetch + AI fit reasons — non-blocking
▼

Two Things Happen in Parallel

  1. Product detail fetch — per-ASIN details (bullets, description, Prime, delivery)
  2. Mini AI enrichment — writes fit_reason + caveat for each pick

Product Detail Provider Order

  • Check per-ASIN detail cache first
  • Rainforest API for cache misses
  • Oxylabs fallback for missing details or missing Rainforest config
  • Oxylabs does a fast first pass, then retries failures in background

Mini Enrichment (AI)

  • Model: gpt-5-mini
  • First locked product framed as hero recommendation
  • Later picks framed as alternatives (who might prefer this over hero)
  • Writes fit_reason + honest caveat per product
  • Token-scoped — won't leak into other sessions
  • Enrichment explains, it does NOT rerank

Key Files

  • backend/lib/handlers/enrichment-handler.js
  • backend/lib/ai-selector.js (miniEnrichSelectedCandidates)

6. Product Modal
Product Detail Modal
Click a row → decision-aid modal opens
▼

Modal Sections (in order)

  1. Image + title (normalized for display; long titles shortened)
  2. At a glance — price, ratings/reviews, optional delivery
  3. Why this pick — AI fit reason (hidden for skipped-refinement previews)
  4. Worth knowing — AI honest caveat
  5. Product notes — feature_bullets or description

Title Normalization

  • Long Amazon keyword-stuffed titles shortened

Hydration

  • Gets smarter as enrichment arrives (fit_reason, caveat, bullets)
  • For preview products → lazy hydration via GET /api/search/product-details

9. Data & Cache Layer
Shared Discovery Cache
Reusable across sessions
▼
  • Scope: rainforest_discovery:v3
  • Key: normalized query + marketplace
  • Normalization: lowercase, spacing, product plural forms
  • Supabase-backed (prod) or local file fallback (dev)
  • Thin entries (<6 items) auto-bypassed on read
  • Zero-price items sanitized on read
  • Stale Amazon links retagged on read
Token-Scoped Session Snapshot
Per-search, per-discoveryToken
▼
  • Created during discovery
  • Contains the candidate pool that finalize rebuilds from
  • Enrichment writes are token-scoped (no cross-session leaks)
  • Also stores query-quality review status
  • This is what discoveryToken points to
Per-ASIN Product Detail Cache
Shared across providers
▼
  • Keyed by ASIN
  • Stores feature_bullets, description, Prime, delivery
  • Shared across all detail providers
  • Late background Oxylabs retries can improve cache quality
Client-Side History
localStorage (signed-out) / Supabase (signed-in)
▼
  • Key: focamai:searchHistory:v1 (localStorage)
  • Saves finalized searches automatically
  • Dedupes by normalized query + follow-up notes
  • Signed-in users → Supabase saved_searches
  • Local entries migrate to account on login
  • Separate from internal search_history telemetry table
10. Query-Quality Review (background)
Background Query-Quality Review
Runs after discovery, non-blocking
▼

Trigger

  • Starts automatically after discovery response is sent
  • Only when OpenAI is configured
  • Stores status on token-scoped snapshot: pending → ready/skipped/failed

Frontend Polling

  • GET /api/search/query-quality
  • Returns ready: false while pending
  • Returns suggestion only for high-confidence, user-visible reviews
  • Returns shouldSuggest: false for quiet/ambiguous/failed
  • Stale poll responses ignored after new search

UI

  • Small inline prompt near refine/results region
  • "Try [suggested query] instead?" / "Keep these results"
  • Accept → starts new guided search with suggested query
  • No automatic query replacement or prewarm
