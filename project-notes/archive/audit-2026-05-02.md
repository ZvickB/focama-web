# Codebase Audit — 2026-05-02

Scope: things to clean up now that Render is the committed long-term backend, and dead code accumulated during development.

**Decision:** Render is the right architecture for this app. SSE, in-flight deduplication, in-process EventEmitter, and in-memory rate limiting all require a persistent server — the codebase has already moved past the point where Vercel serverless is a viable fallback. The Vercel compatibility layer should be cleaned out rather than maintained.

---

## Bugs to Fix

### 1. `express-server.js` imports functions that don't exist
`backend/express-server.js:6-9` imports `handleDiscoverySearch` and `handleLiveSearch` from `server.js`. Neither is exported. The routes `/api/search/discover` and `/api/search/live` on Render will throw `TypeError` when hit.

**Fix:** Remove the two imports and their corresponding route registrations from `express-server.js`.

### 2. SSE enrichment endpoint not registered in Express
`handleEnrichmentStream` is exported from `server.js` and registered in the native HTTP dev server, but is **never registered** in `express-server.js`. On Render, the frontend's `EventSource` call to `/api/search/enrichment-stream` gets a 404 and silently falls back to polling.

The handler is fully implemented — `enrichment-bus.js` and `emitEnrichmentReady` are wired. It just needs one route registration.

**Fix:** Add to `express-server.js`:
```js
app.get('/api/search/enrichment-stream', async (req, res) => {
  await handleEnrichmentStream(req, res)
})
```
And import `handleEnrichmentStream` from `./server.js`.

### 3. `getCountryCode()` reads a Vercel-only header
`backend/lib/rate-limit.js:13` reads `x-vercel-ip-country`. On Render this header is never present, so country code always returns `'US'`. This silently degrades Amazon domain auto-detection for non-US users — they get `amazon.com` instead of `amazon.co.uk`, `amazon.ca`, etc.

**Fix:** Check whether Render or Cloudflare passes a country header and update `getCountryCode` accordingly. If no equivalent header exists, document this as a known limitation.

## Vercel Layer — Clean Out

These exist because Render felt like a commitment at the time. It is now.

### 4. Vercel serverless wrappers (`api/search/*.js`)
All files in `api/search/` directly import and call handlers from `backend/server.js` — they run the full backend as Vercel serverless functions. Now that Render is the committed backend these are not needed, and they can't actually serve as a fallback anymore: SSE, the enrichment bus, and in-process rate limiting don't work in a serverless environment.

**Clean up:** Delete `api/search/` directory. Keep `api/geo.js` — see below.

### 5. `_node-bridge.js` and `_response-recorder.js`
Exist purely to translate Web API (`Request`/`Response`) to Node.js HTTP-style callbacks for the Vercel edge runtime. Not needed on Render/Express.

**Clean up:** Delete `api/_node-bridge.js` and `api/_response-recorder.js`.

### 6. `api/geo.js` — decide what to do with geo
`api/geo.js` reads `x-vercel-ip-country`. If the Vercel layer is removed, there's no geo endpoint at all. The Express server has no `/api/geo` route. Options: find a Render-compatible geo header, drop geo entirely, or keep `api/geo.js` as the one surviving Vercel function since the frontend calls it as a relative path.

**Action needed:** Decide whether geo detection matters before launch and pick a path.

### 7. CORS origin defaults to `focama.vercel.app` in Render config
`express-server.js:20` — the production default is `'https://focama.vercel.app'`. Fine while frontend is on Vercel, but worth updating the default if the frontend ever moves.

## Dead Code

### 8. `FINALIZE_ENRICHMENT_MODE` / blocking path is a no-op
`server.js:1296-1297`:
```js
const configuredEnrichmentMode = getFinalizeEnrichmentMode()
const enrichmentMode = configuredEnrichmentMode === 'blocking' ? 'async' : configuredEnrichmentMode
```
This overrides itself. Setting `FINALIZE_ENRICHMENT_MODE=blocking` does nothing — it always resolves to `'async'`. The function, the env check, and the `enrichmentMode` response fields are dead. `enrichmentMode` only appears in the debug/selection payload, not in any actual logic branch.

**Clean up:** Remove `getFinalizeEnrichmentMode`, the two variables, and their appearances in the response object.

### 9. `candidateAwarePrior` is fetched and never used
`resolveFinalizeCandidatePool` returns `candidateAwarePrior: cachedPrior`, but `handleFinalizeSelection` never passes it to anything — `haikuLockWinnersAndBadges` doesn't accept it. All of this is dead:

- `getStoredCandidateAwarePrior()` function in `server.js`
- The `preRankArtifact` backwards-compat fallback inside it (`server.js:173-177`)
- The `candidateAwarePriorReady` / `candidateAwarePriorGeneratedAt` / `candidateAwarePriorCandidateCount` debug fields in `handleSearchDebug` and `handleRainforestDiscoverySearch`
- `candidateAwarePrior: cachedPrior` in `resolveFinalizeCandidatePool` return value

This was the pre-ranking strategy from before haiku-lock. Fully retired.

**Clean up:** Remove `getStoredCandidateAwarePrior` and all call sites. Remove the debug fields. Leave the `candidateAwarePrior` field in existing cache entries alone — just stop reading it.

### 10. `/api/search/finalize-probe.js`
A debugging echo endpoint. Not registered anywhere, not in the main test suite. No production purpose.

**Clean up:** Delete the file.

### 11. Three identical rate limit config objects
`server.js:44-57` — `LIVE_SEARCH_RATE_LIMIT`, `FINALIZE_SELECTION_RATE_LIMIT`, and `RETRY_ADVICE_RATE_LIMIT` are all `{...DEFAULT_RATE_LIMIT_CONFIG}` with no overrides. Same object three times.

**Clean up:** Replace all three with direct references to `DEFAULT_RATE_LIMIT_CONFIG`.

### 12. `createPreRankArtifact` alias in `ai-selector.js`
`ai-selector.js:553`: `export const createPreRankArtifact = createCandidateAwarePrior` — a backwards-compat alias from a rename. `createCandidateAwarePrior` is not called in the production flow. Both are dead with pre-ranking retired.

**Clean up:** Remove the alias. Remove or demote `createCandidateAwarePrior` if it has no remaining callers.

### 13. Stale mock in `server.test.js`
`server.test.js:57` mocks `takeSharedRateLimitToken` from `search-storage.js`. That export no longer exists — Supabase rate limiting was already removed. Harmless but misleading.

**Clean up:** Remove the `takeSharedRateLimitToken` entry from the `vi.mock('./lib/search-storage.js', ...)` block.

### Prompt B — Fix the Canada/geo bug

```
Project: Focama — Node.js + Express backend on Render, React frontend on Vercel.

CONTEXT
There is a bug where non-US users (confirmed with Canada) always get amazon.com results
instead of their local Amazon store.

The flow:
- `src/components/AmazonStorePill.jsx` calls `/api/geo` on mount (relative path → hits
  Vercel's api/geo.js → reads x-vercel-ip-country header → returns e.g. { countryCode: 'CA' }).
- AmazonStorePill sets local state `detectedCountryCode = 'CA'` and uses it ONLY to show
  a flag emoji and label in the UI. The store (`selectedAmazonDomain`) stays as 'auto'.
- When search runs in `useGuidedSearch.js`, `appendAmazonDomain()` sees 'auto' and does NOT
  add an amazonDomain param to the request.
- The request reaches Render with no amazonDomain. Render calls `getCountryCode()` in
  `backend/lib/rate-limit.js` which reads `x-vercel-ip-country` — that header is not present
  on Render — so it returns 'US'. The search defaults to amazon.com.

The detected country code from /api/geo is effectively thrown away after being used for
display. It never influences the actual search.

PROPOSED FIX
When AmazonStorePill receives a countryCode from /api/geo, resolve it to an actual Amazon
domain using `getAmazonDomainFromCountryCode` (already exported from
`shared/amazon-marketplaces.js`) and store it in the AmazonStoreContext alongside
`selectedAmazonDomain` as a new field `resolvedAmazonDomain`. This field represents the
geo-resolved fallback — it is only used when `selectedAmazonDomain === AMAZON_MARKETPLACE_AUTO`.

In `useGuidedSearch.js`, when building requests, if `selectedAmazonDomain` is 'auto' and
`resolvedAmazonDomain` is available, use `resolvedAmazonDomain` as the amazonDomain param
instead of skipping it. This way Render always receives an explicit domain and never needs
to guess.

The "Auto" UX stays exactly the same — users still see the detected flag and can still
override manually.

Do you agree with this approach? If yes, implement it. The key files are:
- src/contexts/AmazonStoreContext.jsx
- src/contexts/useAmazonStore.js (or wherever the context type is defined)
- src/components/AmazonStorePill.jsx
- src/components/home/useGuidedSearch.js
- shared/amazon-marketplaces.js (read only — getAmazonDomainFromCountryCode is already there)

Run the test suite after and confirm it passes.

After making changes, update these project notes:

- `project-notes/app_flow.md` — in the "Guided backend flow" section, add a note that when
  `selectedAmazonDomain` is 'auto', the frontend now resolves the geo-detected country to a
  domain and sends it explicitly in the request. Remove or update any language implying the
  backend infers the domain from headers.

- `project-notes/current-status.md` — in the "Current backend state" section, remove the
  bullet about `getCountryCode()` reading `x-vercel-ip-country` if one exists, or add a note
  that the country-to-domain resolution now happens on the frontend before the request is sent.
```
