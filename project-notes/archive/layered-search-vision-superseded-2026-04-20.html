Focamai Preferred Layered Search Flow

This version reflects the cleaner approach we agreed on: query framing can start immediately, the refinement question should appear before deeper framing fields finish, candidate-aware prewarm starts only once usable products exist, real cards do not appear too early, and modal explanation can load progressively after the shortlist is already trustworthy.

Parallel Lane

Work that can start immediately from the user query without waiting for discovery to finish.

Main Decision Layer

The shortlist only becomes real after user context arrives and finalize-fast locks the 6.

Secondary Layer

Reasons and drawbacks can load later as long as the cards and modal are already useful.

Parallel Lane A

Query Framing Starts Immediately

This lane can begin from the broad query alone. It does not need to wait for discover results because likely ranking dimensions for a category like wireless headphones exist before specific products are returned.

  • Return one follow-up question as the fastest user-visible output
  • Infer likely tradeoff dimensions in the background
  • Stay lightweight and overrideable later

Parallel Lane B

Discover Builds The Real Candidate Pool

Discovery fetches products, removes junk, cleans duplicates, and prepares the actual candidate set that final selection will use later.

  • Fetch products
  • Clean the pool
  • Prepare shortlist-safe product data
1

User Enters A Broad Product Query

Start

The user starts with the product search itself, like wireless headphones, rather than trying to express every personal preference in the first line.

Goal

Identify the product category and get the search process moving quickly.

Not Yet

This is not the stage where the final recommendation should be locked.

2

Discover And Query Framing Run In Parallel

Immediate overlap

Two lanes begin together: discover works on the actual product pool, while query framing first returns the user-facing question and then continues thinking about likely ranking dimensions from the query alone.

Discover Lane

Fetches and cleans products so later selection works from real candidate data.

Query Frame Lane

Shows the question quickly; richer fields such as comfort, battery, ANC, price, portability, or fit can finish later.

3

Candidate-Aware Prewarm Starts After Usable Products Exist

/api/search/prewarm Depends on candidates

This is different from query framing. Prewarm here is tied to the actual returned products, so it begins only after discover has produced a pool worth reasoning over.

Good Work Here

Baseline ordering, lightweight candidate notes, reusable artifact, candidate-aware structure.

Guardrail

It should stay a prior, not become a cage that blocks later context from changing the outcome.

4

Refine Asks One Useful Follow-Up Question

/api/search/refine

The system asks one short question to learn what really matters, rather than pretending the first broad query already told it enough. This question should be the first useful AI output the user sees, not something blocked behind all later field reasoning.

Example

What matters most here: comfort, battery, price, or something else?

UI Rule

Show the question as soon as it is ready; keep richer framing fields in the background.

5

User Adds Context

Strongest signal

The user now says what actually matters. This should heavily reweight the later decision, even if the early query frame or prewarm artifact was leaning in another direction.

Example

I want the most comfortable pair for long work sessions and I want to stay under $250.

Important Rule

If discover surfaced something surprising but strong, finalize should still be free to notice it here.

6

Finalize-Fast Picks The Real 6

/api/search/finalize Actual shortlist

This is the true decision layer. It uses the real candidate pool, the user’s context, the early query frame, the prewarm artifact, and supporting trust signals, but user context carries the most weight.

Must Return

Trustworthy card-safe data for the chosen 6 so the UI does not reveal half-baked recommendation cards.

Should Not Wait For

All richer reason writing and drawback polish if those can be safely moved into a second layer.

7

Only Now Do The Real Cards Reveal

Results first

We removed the too-early preview-card idea here. Recommendation-like cards should only appear after the shortlist is genuinely settled and card-safe fields are ready.

Cards Already Have

Image, title, price, merchant, ratings, reviews, link, and any lightweight deterministic presentation.

Reason For This Choice

Users should not anchor on provisional recommendations that might still shift in meaningful ways.

8

Background Enrichment Explains The Chosen 6

Second layer

Once the shortlist is locked, a lighter second pass can generate stronger fit reasons, drawbacks, and modal-ready explanation for those same 6 items.

Good Output

Why this fits, what to watch for, maybe a short best-for note.

Guardrail

This layer should enrich the shortlist, not quietly re-rank it or question who won.

9

Modal Opens Immediately, With Explanation Loading If Needed

Progressive modal

If the user taps before enrichment is ready, the modal still opens with core product facts. Only the explanation sections should show loading states or skeletons.

Preferred UX

The modal is useful immediately and gets richer as explanation arrives.

What We Avoid

Blocking the whole modal or pretending the card is ready when the basic data still is not.

10

Retry Reuses The Same Structure

Same model

If the user rejects the shortlist, their retry feedback becomes the new strongest signal, finalize-fast runs again, and enrichment reruns for the new chosen 6.

What Stays Stable

Early layers still help, but they remain overrideable by the latest user feedback.

Why This Matters

The system stays flexible instead of getting trapped by its first assumptions.

The Core Rule

Early layers prepare. Later user context decides.

1

User Context

Budget, comfort, durability, style, use case, and what to avoid should outweigh earlier guesses.

2

Core Relevance

The product still has to truly fit the original product query.

3

Quality Signals

Ratings, reviews, merchant trust, and price sanity support the choice.

4

Early Scaffold

Query framing and prewarm are helpful priors, not hard rules.

Compact Summary

  1. Broad query starts the flow.
  2. Discover and query framing run in parallel.
  3. The follow-up question returns first; richer framing fields continue later.
  4. Candidate-aware prewarm starts once usable products exist.
  5. User adds context after one short refinement question.
  6. Finalize-fast picks the real 6.
  7. Only then do recommendation cards reveal.
  8. Reasons and drawbacks can enrich the modal afterward.
